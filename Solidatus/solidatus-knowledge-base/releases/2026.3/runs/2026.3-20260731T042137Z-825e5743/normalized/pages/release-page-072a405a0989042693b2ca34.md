## Ownership and responsibility for connectors

When a user saves or merges changes to a model via the user interface, the user that saved or merged the model is named as the author of the resulting revision. Other users may also be noted as contributors to changes, perhaps because they updated a task model, but the responsibilities for changes are clear.

When a model is updated via the [connector framework](/connectors/connectors-overview/connectors-framework), there is a separation of responsibilities for each action involving a connector.

| **Controlling access to models**                      | Users that own models to be updates by connectors are not required to be involved in the connector framework, though they can be. Owners of models only need to ensure that the user or service account that owns the [job token](#job-token) has at least *Author* access to every model that would be updated by the job. If service accounts own connector forks that will be updated, they need to share forks with any user who creates a job to update them. |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Registering a connector with a Solidatus instance** | Before a connector can be registered, a user (possibly a [service account](/connectors/connectors-overview/service-accounts)) must generate an [agent token](#agent-token). The account that generates the token is the initial owner of the agent when the connector is registered.                                                                                                                                                                               |
| **Controlling access to agents and jobs**             | Users that initially control access to agents and jobs are the users that created the agent tokens and job tokens. See [agent roles](#agent-roles) and [job roles](#job-roles) to find out more about the different roles available.                                                                                                                                                                                                                               |
| **Model permissions**                                 | The user that owns the job token must have at least *Author* access to every model that would be updated by the job. If the job creates new models or forks, they will automatically be owned by the owner of the [job token](#job-tokens).                                                                                                                                                                                                                        |
| **Running the connector job**                         | The job run history identifies the user or external agent (scheduler, etc.) that ran the job. Any user with at least `Execute` permissions for a connector job can run it.                                                                                                                                                                                                                                                                                         |
| **Owning the model changes**                          | The job takes responsibility for changes to models. It does not matter which user ran the job — the job is named as the author of the revision created by the job run.                                                                                                                                                                                                                                                                                             |

If the model that is updated has been imported into other models, standard Solidatus features automatically create an [imported model update](/models/share-and-collaborate/activities-and-activity-types/import-model-updates) Activity for every model affected. The owner of the job token (the *Framework user* in the diagram below) is named as the author for each of those Activities.

## API tokens and permissions

API tokens allow connectors to use the Solidatus API. A token is used to authorise API calls much like a password.

Each token is assigned one or more permissions when it is created (for example, `Fork model`, which enables an API call with that token to fork a model). You should follow the principle of least privilege when assigning permissions - give the token the least amount of access that is needed to get the job done. This ensures that should a token be compromised, it will be least damaging.

See [API tokens for connectors](/api-documentation/api-overview/api-authentication) for more information about creating and revoking API tokens.

### Agent tokens

Every agent is registered using a token, which allows the external software (the connector) to access Solidatus. The token is generated by a user or service account and will need to be supplied to whoever installs the connector.

The agent token cannot be amended via the user interface; if a new token is required, the connector needs to be re-registered. To re-register the connector, you must first of all [deactivate the existing agent](/connectors/connectors-overview/agents#deactivating-an-agent).

It is vitally important for the token used to register the agent to have sufficient permissions to carry out actions required by the agent. For example, the `Create model` permission is required to create a model. See [minimum permissions for connector tokens](#minimum-permissions-for-connector-tokens).

### Job tokens

It is vitally important for the *job token* to have sufficient permissions to carry out the actions required by the job. For example, the `Fork model` permission is required to create a model fork. See [minimum permissions for connector tokens](#minimum-permissions-for-connector-tokens).

The job token can be amended at any time via the [Job Overview](/connectors/connectors-overview/jobs#job-overview).

### Minimum permissions for connector tokens

It is vitally important for the *agent token* and *job token* to have sufficient permissions to carry out the actions required by the connector. The following table show the minimum token permissions required for several scenarios.

|                                                           | **Agent token**                                             | **Job token**                                               |
| --------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------- |
| **Read-only connector** (does not update models or forks) | `View model` - see Note 1                                   | `View model` - see Note 1                                   |
| **Updating existing models/forks**                        | `View model` - see Note 1                                   | `View model` - see Note 1                                   |
| **Creating new forks**                                    | `View model` - see Note 1; also `Fork model` - see Note 1   | `View model` - see Note 1; also `Fork model` - see Note 1   |
| **Creating new models**                                   | `View model` - see Note 1; also `Create model` - see Note 2 | `View model` - see Note 1; also `Create model` - see Note 2 |

1. user that owns the token (or owns the service account that owns the token) must also have at least author for model / fork to be updated
2. token owner (as above) will own any models/forks created by the job

### Which user owns the token?

Tokens can be owned by ‘real users’ or by service accounts. Service accounts facilitate a separation of responsibilities - essential when managing automated metadata ingestion via connectors.

## Share connectors

You can share connectors by sharing an agent, whereby another user can create and run jobs, or by sharing jobs, whereby they can view, run, or edit them.

### Agent roles and permissions

Connector agents (and their jobs) can be private to a single user or shared with a group of users, allowing consistent and efficient auto-creation or update of Solidatus models.

Users only have access to an agent if they have been granted a role personally for that agent, or have inherited a role via their membership of one or more Groups.

The user that owns the agent token used to register the connector and create the agent, is automatically assigned as the first owner of the agent; if the token belongs to a [Service Account](/connectors/connectors-overview/service-accounts), the users that own the service account are also owners of the agent. See [Operating a Service Account](/connectors/connectors-overview/service-accounts#step-5-register-an-agent-using-a-service-account-token) for more information.

There are four agent roles that provide permissions to act on an agent - the table below sorts them left-to-right, from the most privileged to the least privileged.

|                         | **Agent Owner** | **Agent Editor** | **Agent User** | **Agent Viewer** |
| ----------------------- | --------------- | ---------------- | -------------- | ---------------- |
| **Delete agent**        | Yes             |                  |                |                  |
| **Edit agent settings** | Yes             | Yes              |                |                  |
| **Edit Permissions**    | Yes             |                  |                |                  |
| **View agent**          | Yes             | Yes              | Yes            | Yes              |
| **View jobs**           | Yes             | Yes              | Yes            | Yes              |
| **Create jobs**         | Yes             | Yes              | Yes            |                  |
| **Delete jobs**         | Yes             |                  |                |                  |

#### **Sharing agents with Groups**

Agents can be shared via Groups and agent roles can be set at the group level, in which case all members of a Group have the role given to the Group.

Users might belong to several Groups with which the same agent has been shared. When that happens and the roles given to each group are different, the effective role of a user is the most privileged of the roles they have been assigned.

For example, let's say the user called `Justine Thyme` has several roles for an agent - their effective role is *Owner*, the highest privilege they have been granted (via `Group B`):

| **Role** | **Assigned**                      |
| -------- | --------------------------------- |
| Viewer   | personally, on the Agent Overview |
| Editor   | via `Group A`                     |
| Owner    | via `Group B`                     |
| User     | via `Group C`                     |

The roles for an agent can be viewed and managed in the [Agent Overview](/connectors/connectors-overview/agents#agent-overview).

{% hint style="info" %}
A user that has access to an agent through the user interface might not have access to the agent’s jobs, or to the models updated by those jobs. Each job and model has its own distinct set of users and permissions.
{% endhint %}

### Job roles and permissions

{% hint style="warning" %}
It is crucial for the job token to be granted sufficient permissions to carry out the actions required by the job.
{% endhint %}

The user that creates a job is automatically assigned as the initial owner of the job; if that user is a [Service Account](/connectors/connectors-overview/service-accounts), the users that own the Service Account are also owners of the job. See [Operating a Service Account](/connectors/connectors-overview/service-accounts#step-5-register-an-agent-using-a-service-account-token) for more information.

There are four job roles (and one agent role) that provide permissions to act on a job - the table below sorts them left-to-right, from the most privileged role to the least privileged role.

|                      | **Agent Owner** | **Job Owner** | **Job Editor** | **Job Executor** | **Job Viewer** |
| -------------------- | --------------- | ------------- | -------------- | ---------------- | -------------- |
| **Delete job**       | Yes             | Yes           |                |                  |                |
| **Edit job**         | Yes             | Yes           | Yes            |                  |                |
| **Edit Permissions** | Yes             | Yes           |                |                  |                |
| **View job**         | Yes             | Yes           | Yes            | Yes              | Yes            |
| **Run job**          | Yes             | Yes           | Yes            | Yes              |                |

#### Sharing jobs with groups

Users have access to a job if they have been granted a role for that job, or have inherited a role via their membership of one or more Groups.

Their effective role is the most privileged of the roles they have been assigned. For example, the user called `Justine Thyme` has several roles for a job, shown in the table below. Their effective role is *Owner*, the highest privilege they have been granted (via `Group B`):

| **Role** | **Assigned**                    |
| -------- | ------------------------------- |
| Viewer   | personally, on the Job Overview |
| Editor   | via `Group A`                   |
| Owner    | via `Group B`                   |
| Executor | via `Group C`                   |

The roles for a job can be viewed and managed in the [Job Overview](/connectors/connectors-overview/jobs#job-overview).

{% hint style="warning" %}
The job token must have been created by a user or [Service Account](/connectors/connectors-overview/service-accounts) with at least *Author* access to the required models).
{% endhint %}

### Job roles vs model roles

Users (including Service Accounts) may have access to agents, jobs, or the models created or updated by jobs. The following table illustrates the *minimum* access required for each step in the process from creating a job to reviewing the effect of a job on models.

For example, a user can only edit a job, execute the job, and review the results if they have the *Executor* role for the job, and at least the *Viewer* role for all affected models.

|                                 | **Create a job** | **View a job** | **Edit a job** | **Run and monitor a job** | **Review model changes** |
| ------------------------------- | ---------------- | -------------- | -------------- | ------------------------- | ------------------------ |
| **Token owner requires**        |                  |                |                |                           | Author                   |
| **Minimum job role required**   | (Agent) Editor   | Viewer         | Editor         | Executor                  |                          |
| **Minimum model role required** |                  |                |                |                           | Viewer                   |

See [best practices for service accounts ](/connectors/connectors-overview/service-accounts#best-practices-for-service-accounts)for advice on when to use service accounts instead of ‘real’ users.
{% endhint %}
