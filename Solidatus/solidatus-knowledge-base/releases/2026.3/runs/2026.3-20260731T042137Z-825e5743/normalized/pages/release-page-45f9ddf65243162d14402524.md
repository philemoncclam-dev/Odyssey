# Connector framework

The **connector framework** is an architecture for integrating connectors with the Solidatus user interface that makes developing and running connectors simpler and faster.

## Connector framework overview

Connector processes run outside the core Solidatus application. To manage and run them through the Solidatus user interface, you must first register them with Solidatus. When you register a connector, an [agent](/connectors/connectors-overview/agents) representing the connector appears in connector interface.

A connector agent contains the information required to run the connector process and perform specific actions called [jobs](/connectors/connectors-overview/jobs) or [job runs](/connectors/connectors-overview/running-a-job). The information needed to identify the external source and target model for an individual connector action must be provided in the [job configuration](/connectors/connectors-overview/jobs#settings-tab) for an individual [job](/connectors/connectors-overview/jobs).

The steps involved in setting up an running a connector stem from the architecture of the connector framework.

### **Example: The Database connector**

Registering the JDBC connector with a Solidatus host creates an [agent](/connectors/connectors-overview/agents) for the JDBC connector, available in the connector interface inside Solidatus. The account that owns the API token used to register the agent also owns the agent, and initially the agent only appears in the connector interface of that account. The agent can then be shared with other users through the [agent's settings](/connectors/connectors-overview/agents#settings-tab).

{% hint style="info" %}
We advise that you use **service accounts** to register, manage, and share agents across an organisation. See the [service accounts page](/connectors/connectors-overview/service-accounts) for the why's and how's of service accounts.
{% endhint %}

A separate [job](/connectors/connectors-overview/jobs) for an agent must be created for each unique combination of external source and target Solidatus model. If you are extracting different data elements or structures within the same source technology, unique jobs must be created for each unique set of source data structures (e.g., schemes, tables, etc.).

Let's say you want to extract information from a specific Data Warehouse database into a specific model fork. The job configuration provides the connector with the identifying information (IDs) and permissions for the database in the Data Warehouse, as well as for the model fork in Solidatus.

{% hint style="info" %}
We advise that connector jobs always target a fork of a model, which we often referred to as a "**connector fork**", rather than an original atomic model. This separates the raw model built by the connector from the model in which manual changes and model design can be introduced.

Results of the connector job can be merged into a parent atomic model via [pull requests](/models/build-and-edit-models/forks) without overwriting design changes to the parent atomic model. See the [model topology](/solidatus-best-practice/model-topology) page in our best practice section for more information and explanation.
{% endhint %}

The same job can be executed any number times to refresh a model with changes in the external source system. **IMPORTANT: The Solidatus model a job is targeted to import into is overwritten by incoming model data each time the job is executed**.

You can configure connectors to create a new model with the output of a job or to create a new revision on an existing model each time the job is finished running.

## Agent mode vs. standalone mode

Most of our connectors can be run in either agent or standalone modes (see [connector-specific documentation](/connectors/connector-specific-documentation) for specifics on how to run each connector in either mode).

**Agent mode** sets up a connector agent in the user interface that, while active, waits for and receives jobs sent to it via the user interface.

**Standalone mode** runs one execution of the connector via the command line with the specified configuration parameters and then stops.

## Connector high-level architecture

<figure><figcaption><p>Connector framework architecture</p></figcaption></figure>

1. A job is triggered by user in the UI, via API.
2. The agent receives the job request and executes it, connecting to the data source and requesting metadata.
3. The agent receives metadata from the data source, interprets it, and creates a Solidatus model.
4. The agent publishes the Solidatus model to a Solidatus host environment.

## Encryption

All communication between Solidatus and a connector are encrypted. An encryption key is generated when the connector is registered. If required, a new encryption key can be generated via the [Agent Overview](/connectors/connectors-overview/agents#agent-overview).

### Troubleshooting <a href="#troubleshooting" id="troubleshooting"></a>

If there are technical issues when running the connector or the connector has been upgraded, you may need to re-register the connector. Before you can re-register a connector, you must de-activate the existing agent it via the [Agent Overview](/connectors/connectors-overview/agents#agent-overview).

### Technical Notes <a href="#technical-notes" id="technical-notes"></a>

**Installation**

MongoDB requirement: MongoDB replicaset enabled (<https://docs.mongodb.com/manual/replication/>)

MongoDB requirement: change streams (<https://docs.mongodb.com/manual/changeStreams/>)

Solidatus UI: websockets is recommended for the best user experience

Connectors are distributed as Docker images or Helm charts, and can also be distributed as zip, jar, “exe” if necessary

**Using connectors**

Connector jobs run outside of the Solidatus main application process

Each connector has its own agent process

Each connector defines and requires its own job configuration and user interface metadata

Each connector (such as the JDBC connector) can have multiple agents running at the same time

Multiple jobs can run for an agent at the same time as determined by the connector (this is supported by the SDK)

The stages of every job run can be followed and the results are available through the user interface
