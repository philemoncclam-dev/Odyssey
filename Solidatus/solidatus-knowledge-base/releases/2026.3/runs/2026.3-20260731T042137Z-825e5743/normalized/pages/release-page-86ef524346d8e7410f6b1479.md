# Configure a context model

A **context model** organizes and summarizes lineage in a Data Map by grouping related entities into meaningful business categories.

Context models are simply Reference models, but ones built and designed to visually group a Data Map and provide high-level classifications for data structures represented in a Data Domain.

This page covers the steps involved in creating and configuring a context model:

## Preliminary design considerations

Before building a context model, it's helpful to do some planning to determine which high-level terms and categories best capture how data is organised and used in your business.

There are two key restrictions on relationships to context models for Data Map grouping to render successfully:

1\) Each entity in lineage models can only be related to **one** term in a context model.

> Note that both [**direct** and **inherited** reference relationships](/models/understand-solidatus-models/understand-reference-relationships#direct-inherited-and-inferred-relationships) count towards the number of relationships an entity has to a context model, as is entailed by the combination of this first rule and the following second rule.

2\) Entities must be related to the **same context term as ancestors and descendants**.

Given these rules, context models work best for scenarios where entities only belong to one business classification category.

For example, a table can only appear in one database container, and the database container can only be contained by one system container. So, using a context model for mapping to systems-databases-tables is a good option.

For some scenarios, such as mapping to business processes where the same data might be used in multiple processes, context models may not be a good fit. In those cases, it would be better to map to a business process Reference model that is not used for visual grouping in a Data Map.

### Best practice for context models

Each Data Domain should contain **only one** context model for grouping the Data Map.

The context provided should be clearly relevant to the name and purpose of the domain. This way, those who access a domain immediately understand the lens through which technical information is organised and presented.

If you'd like to view the same lineage from a different context perspective, create a new domain and add a different context model along with the same lineage models.

## Step 1: Build a Reference model

Once you've decided on your context model's purpose, building it follows the ordinary steps of model building: create a new Reference model and add terms and term hierarchies you want to use to group your Data map.

### **How context grouping works**

If entities in Lineage models have reference relationships to terms in a context model and the context is applied to a Data Map, entities are embedded in a grouping container representing the term they are related to.

When the grouping container is expanded, all entities related to the term appear inside it.

For example, let's say *Mortgage DB (Oracle)* is a term in a context model and *mortgagesystem* is an Object in a Lineage model with a reference relationship to *Mortgage DB (Oracle) .*

<figure>../_images/expand-context-box.png<figcaption></figcaption></figure>

When the context model containing *Mortgage DB (Oracle)* is applied to the Data Map, *mortgagesystem* is embedded inside an expandable grouping container representing *Mortgage DB (Oracle)* and is only visible when *Mortgage DB (Oracle)* is expanded.

### Best practice for context model design

There are a few points of best practice to keep in mind when designing a context model:

#### **Keep context model structure simple**

The simplest context model structure, which is the easiest to configure for a Data Map, is one in which the model is "flat" without hierarchy: all context terms are **Layers** and all are at the same level.

<figure><figcaption></figcaption></figure>

This example shows a very simple context model made up of four layers, each representing high-level systems that make up part of the technical infrastructure through which a business processes data.

When applied to a Data Map, a single-level context model generates single-level context grouping boxes in which related lineage entities are embedded.

<figure><figcaption></figcaption></figure>

When these containers are expanded, the entities in lineage models with reference relationships to these high-level terms appear inside the corresponding container.

The example shows that context models provide high-level, business friendly summaries of a technical landscape. They enable you to drill down into technical lineage through the visual lens of meaningful business structures and functions.

#### **Context term hierarchy generates grouping hierarchy**

You can create hierarchically nested context containers in a Data Map.

If context terms are Objects, Groups, or Attributes in the context model, the Data Map generates *hierarchically nested* context grouping boxes.

**Entities appear in the grouping box representing the lowest-level term to which they have a reference relationship.**

For example, if the lineage entity *mortgagesystem* is related to a term *Mortgages* that is a child of *Lending,* and *Lending* is a child of Products, *mortagesystem* will be embedded in grouping containers with the hierarchical structure *Products*>*Lending*>*Mortgages.*

## Step 2: Map relationships to a context model

Reference relationships between Lineage model entities in a Data Domain and context model terms determine how the Data Map groups and displays your data landscape when context is applied.

### Context relationship mapping rules

There are several rules that must be followed when mapping relationships from entities in Lineage models to context model terms. These

1. **One relationship per entity:** Each entity can only be related to one context term. If this rule is broken, the Data map fails to render when context is applied.
2. **Context relationship inheritance:** Descendants automatically inherit their ancestor’s context grouping relationship. This means you don't have to create a relationship for every entity in a domain. Relationships should be created at the highest level in a hierarchy.
3. **No conflicting relationships within a hierarchy:** Don’t relate ancestors and descendants to different context terms (entailed by the combination of rules 1 and 2).
4. **No entity type mixing within a hierarchy:** You can create relationships to context models at any entity-type level (Layer, Object, Group, Attribute), but avoid mixing the entity type level within the same hierarchy (this makes violating rules 1 and 3 likely).

#### **How relationship inheritance works**

Relationship inheritance means that descendant entities automatically inherit a reference relationship to a context model term from their ancestor entities (parent, parent's parent, etc.).

Since context relationships are inherited:

* you don’t need to create a reference relationship for every entity in a Data Domain. If you relate a Layer in a lineage model to a context term, all of its descendants (Objects, Groups, Attributes) automatically appear in the same container in a Data map.
* a Data Map cannot be rendered if an entity is related to a different context term from a descendant or ancestor entity in its hierarchy.

#### **Entity types and context mapping**

Of course, relationships should be created at the level appropriate to how your data flows map to business context terms.

You can create relationships between context model terms and Layers, Objects, Groups, or Attributes in a Lineage model, **but be careful not to mix the level at which relationships are created within the same hierarchy**.

For example, if you create relationships to context model terms at the Object level within a Layer:

* Objects in the same Layer can be grouped into different context model categories
* The Layer cannot be related to a context term and it will not appear in the Data Map when the context is applied

#### **Context mapping tips**

* It's simplest to select an entity type in the set of Lineage models published to a single domain – Layer, Object, Group, or Attribute – and only add context relationships to entities of that type
* For more complex cases, different entity types can be related to different context model terms, but avoid doing that within the same hierarchy. For example, you can create context relationships to a Layer and then to only Objects in another Layer, and to only Groups in another Layer

For general instructions on how to create Reference relationships between a Lineage model entity and a Reference model term, see [Add and Edit Reference Relationships](/models/build-and-edit-models/add-and-edit-reference-relationships).

### Unmapped entities

You might not have mapped some entities in Lineage models published to a Data Domain to any terms in a context model that you apply to a Data map. When you apply the context model, what happens to these entities?

Data maps group all unmapped entities into a container named **Untagged**.

<figure>Hierarchical context categories<figcaption></figcaption></figure>

{% hint style="success" %}
Since entities inherit the context grouping category of their ancestors, “untagged” entities are entities whose ancestors are also unrelated to any context term.
{% endhint %}

### Add colours to context containers

You can customise the colours of context grouping boxes in a Data Map to make data flows and high-level summaries easier to interpret.

<figure><figcaption></figcaption></figure>

The colour of a context grouping box can be configured by adding the property **SOL.Context.Colour** (case-sensitive) to the corresponding term in the underlying context Reference model (see [Add context models to a domain](#add-context-models-to-a-domain)).

<figure><figcaption></figcaption></figure>

**Context terms don't inherit their colour from ancestor terms.** As a result, each term, even in the same hierarchy, must have a value for the **SOL.Context.Colour** property to appear in colour in the Data Map.

For example, for *Products* **and** its child term *Mortgages* to appear green, both must have the **SOL.Context.Colour** property set to green.

Terms in the same hierarchy can be given a different colour from ancestors and descendants.

Whether terms in a hierarchy have the same or a different colour, the **SOL.Context.Colour** property must be given to each term.

<figure><figcaption></figcaption></figure>

For example, even if a high-level *Products* term does not have direct reference relationships to entities in the Lineage models published to a domain, it appears in the Data map because its child term, *Mortgages*, does. For *Products* to have a colour, it must have the **SOL.Context.Colour** property with a valid value.

#### **Colour value specification**

Colours can be specified in any of the following formats:

* CSS colour words — e.g., <mark style="color:$primary;">`red`</mark>, `green`, `blue`
* Hexadecimal colour values — e.g., `#FF0000` (red), `#00FF00` (green), `#0000FF` (blue)

{% hint style="success" %}
Data Maps do not support colour transparency; only the 6-digit hex format can be used
{% endhint %}

## Step 3: Publish context models to a domain

After you’ve built your context model and mapped relationships to the Lineage models in a domain, you then need to add it to the same domain as the Lineage models you've mapped it to.

{% hint style="success" %}
You can add a context model either when you create a domain or later through the [domain settings](/data-domains/build-data-domains/edit-data-domains#data-map-settings).
{% endhint %}

To add a context model to a domain:

1. Navigate to the `Settings` of the Data Domain (see [Edit a Data Domain](/data-domains/build-data-domains/edit-data-domains)) or create a new domain.
2. Publish the Reference model you designed to be a context model by selecting it in the `Models` tab and clicking **SAVE** in the top right.

<figure><figcaption></figcaption></figure>

## Step 4: Designate the Reference model as a context model in Data Map settings

When you publish a Reference model to a domain, it then appears in the `Data Map` tab.

{% hint style="success" %}
We recommend that you only **add one context model per domain** to simplify the structure and use case objective of a Data Domain. If you'd like to group the same lineage models by another set of context categories, create a new domain for that context model.
{% endhint %}

<figure>Select *Context* models for use with the Data Map<figcaption><p>Select <em>Context</em> models for use with the Data Map</p></figcaption></figure>

The `Data Map` tab of the domain settings contains **all and only** Reference models that you published in the `Models` tab.

In the `Data Map` tab, you can designate Reference models to function as context models, i.e., they are then available to apply to visually group a Data Map.

When you designate a Reference model as a context model, it becomes available in the list that appears when you open a Data Map and in the dropdown menu inside a Data Map.

<figure>Select Context to apply to a Data Map<figcaption><p>Select Context to apply to a Data Map</p></figcaption></figure>

The *Physical lineage* option is always available in all Data Maps. It allows you to display raw, aggregated lineage from all published Lineage models without any context grouping.

## Context models and Data Assets

Context models can be mapped to Data Assets in the same way as non-asset entities: create reference relationships between context model terms and entities that are Data Assets in the underlying Lineage models published to a Data Domain.

The key difference between mapping Data Assets and non-asset entities is that the same Data Asset likely appears in several models in the same domain. Accordingly, you should map each entity representing a top-level asset in each Lineage model containing that asset to the same context term.

{% hint style="info" %}
It is possible to embed entities representing the same asset in two different context containers by relating top-level assets to different terms, but this is not the standard scenario.
{% endhint %}

Here is a high-level summary of the steps:

1. Open the set of Lineage models in a Data Domain that contain Data Assets (You must have at least an **Author** role on a model to complete these steps)
2. Find entities representing Data Assets in those lineage models

> You can use the [Data Assets sidebar tab](/the-user-interface/models-ui/model-viewer/model-viewer-sidebar/data-assets-tab) to locate entities that are Data Assets in a model.

3. Add a reference relationships to context terms to **top-level assets** in the model. Since context relationships are inherited, only top-level assets should be related to a context term.

You should create reference relationships to the same context model terms in each model that contains a given Data Asset.

## Troubleshooting

**My context model isn't available in the Data Map**

* Verify that you published the Reference model built to function as a context model to your domain
* Verify that you designated the Reference model as a context model in the [Data Map settings](/data-domains/build-data-domains/edit-data-domains#data-map-settings)

**My entities aren’t grouping correctly**

* Check that relationships exist between your lineage entities and context terms
* Verify entities at most **one relationship to a context model**
* Check that entities have the same context relationship as ancestors and descendants

**Context boxes are empty**

* Verify relationships between context terms and lineage entities in the underlying Lineage models

**Too many “Untagged” entities**

* Review which entities lack relationships to context terms
* Consider if your context categories cover all relevant lineage entities
* Check if unmapped entities should have relationships or belong in “Untagged”

**Nested groupings aren’t working**

* Check that relationships are created to the correct level in the term hierarchy
* Ensure the hierarchical structure of terms matches your intended business structure

**Can’t see my Context model in the dropdown**

* Confirm the model is published to the domain in `Settings` → `Models` tab
* Check that it’s designated as a Context model in `Settings` → `Data Map` tab
* Make sure you’re viewing the Data Map in the correct domain
