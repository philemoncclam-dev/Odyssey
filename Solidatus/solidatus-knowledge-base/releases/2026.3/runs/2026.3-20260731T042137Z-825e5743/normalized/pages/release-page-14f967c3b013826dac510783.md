# Webhooks

{% hint style="warning" %}
Once a webhook has been enabled on an account, it will trigger for **every model that the account has any level of access to** when an event of the specified type occurs. So, it is advisable to set up webhooks only on Service Accounts whose access is restricted to models they are used to update. See [Using Webhooks with Service Accounts](#use-webhooks-with-service-accounts).
{% endhint %}

Webhooks are HTTP POST requests in JSON format that trigger whenever an event of a specified type occurs. Solidatus will send a payload containing the event details and supporting data to a target URL that must be separately configured to receive it.

Webhooks can be used as external notifications to keep track of model events in real-time. But they also enable Solidatus events to trigger actions/events in another system. For example, a webhook request can automatically call the API of another system when Solidatus models are updated or metadata is changed. The more ambitious vision for webhooks is to make Solidatus a central part of an automated workflow of discrete, connected systems, in which changes to a model call other actions/events downstream.

Once a webhook is switched on, **anyone** with access to the recipient URL – regardless of whether they have access to Solidatus – will be able to keep track of specified model events.

Each webhook will send a payload to **one** unique recipient, so multiple webhooks must be configured if notifications of the same event are to be sent to multiple recipients.

{% hint style="info" %}
All accounts are subject to a licence-controlled monthly limit on the total number webhooks that can be sent per calendar month. By default, the limit is set to 50 total webhook requests per month for each user with the `CreateWebhook` capability, but it is summed across all user roles (i.e., if a user has both author and admin roles, the total will be 100).

If the limit is exceeded, no webhook requests will be sent, but a history of unsent requests will be kept - see [Manage webhooks](#managing-webhooks). To increase your webhook limit, contact your Solidatus sales manager.
{% endhint %}

## Webhook target requirements

The Solidatus server will make HTTP POST requests to the configured webhook URL.

By default, only HTTPS targets are allowed (i.e. `https://` target URL), but this requirement can be relaxed to allow HTTP – contact [support@solidatus.com](mailto:support%40solidatus.com) for assistance.

## Create a webhook

Webhooks can only be created and configured by users with the `CreateWebhook` capability, usually provided via the [Author licence](/account-management/licences-capabilities-and-roles) but by default added to any role that has the `CreateModel` capability. As with all capabilities, it is licence dependent.

To create a webhook:

> 1. Navigate to the [Webhooks](/account-management/account-settings) page by clicking on your initials in the top right of [the navigation bar](/the-user-interface/the-navigation-bar), selecting *Account*, and scrolling down to the *Manage Webhooks* section. Click the **Manage Webhooks** button.
> 2. Click **+ Create** to create a new webhook.
> 3. Give your webhook a name in the *Name* field and add the URL of the recipient in the *URL* field. The recipient URL must be configured separately at the target endpoint to receive these HTTP POST requests.
> 4. At least one event type must be selected, and webhooks currently support one event type: `NewModelRevision`. This will trigger the webhook whenever a Model revision is saved for any Model that the account has any level of access to.
> 5. Click **Test Connectivity** to test if your webhook was successfully received. You can also view the payload request and response in the **Connectivity** tab.

{% hint style="success" %}
For secure communication, Solidatus supports the ability to sign webhook payloads with a `secret` HMAC signature per the WebSub standard.

The recipient must be configured separately to receive the secret signature you choose and this capability must enabled as a configuration setting on your Solidatus instance - contact [support@solidatus.com](mailto:support%40solidatus.com) for assistance with this.

If you have this feature enabled, you will see a `Secret` field when you create a webhook that can be filled in with a signature you chose.
{% endhint %}

## Use webhooks with Service Accounts

Because webhooks trigger for every model that an account has any level of access to (i.e., as a Viewer, Author, or Owner), it is best to configure them only on [service accounts](/connectors/connectors-overview/service-accounts) to keep track of the automated activity of connectors or to build an automated workflow between connected systems.

In either scenario, set up webhooks on the service accounts that provide the [API token](/connectors/connectors-overview/users-and-tokens#api-tokens) used by connectors. This ensures that webhooks are triggered when models are automatically updated via the connector.

T configure webhooks on service accounts, [impersonate the service account](/connectors/connectors-overview/service-accounts#step-3-generate-an-api-token-for-the-service-account), then in follow the steps listed in the [Creating a webhook](#creating-a-webhook) section.

## Manage webhooks

All webhooks that have been configured on an account are listed on the `Webhooks` page. You will see the name of the webhook, the recipient URL, the event types that trigger the webhook, and options to manage or delete the webhook.

You will also see a toggle next to the recipient URL that switches the webhook on or off.

<figure><figcaption></figcaption></figure>

Click `Manage` to open a new dialogue that you can use to edit, review, and test your webhook. The SUMMARY tab is used to edit webhook names, reciepient URLs, and event types that trigger the webhook. The CONNECTIVITY tab allows you to test a webhook and view the JSON request payload and response.

The HISTORY tab stores requests and responses for 7 days. This history is especially useful for troubleshooting any failed requests, and failed requests can be easily found by looking for the red `X` on the left of an entry. You can also view the request payload and response of any webhook here.
