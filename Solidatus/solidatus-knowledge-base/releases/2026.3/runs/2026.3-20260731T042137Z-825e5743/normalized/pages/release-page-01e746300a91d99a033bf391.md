# Tasks

A **Task** is a defined piece of work on a model that is assigned to one or several registered Solidatus users to complete. When a task is created, a new, unique model is created for the task, so proposed changes are not immediately applied to the “master” version of a model.

Using tasks, you can :

* Collaborate and share the work of building and editing models.
* Create a division of labor and responsibility for editing different parts of a model.
* Make changes without committing them directly to the “master” version of a model.
* Establish an approval and review process for committing changes to a model.

You can also customise how much review is required before changes in a task are merged into a model:

* Changes made in a task can be merged in automatically when the task is submitted (enable `auto-merge` and set the minimum number of approvals to 0).
* You can require that any model *Owner* and *Author* manually merge changes made in a task (disable `auto-merge` and set the minimum number of approvals to 0).
* You can enable the `Approvals Workflow` to require a more formal review and either accept and merge changes, or reject them and send them back for further work (set minimum number of approvals to > 0).

You can modify the merging and approval settings for tasks in the `Activities` settings in the Model Overview of a model.

{% hint style="success" %}
Tasks are similar to forks in that they create copies of a model that can be edited independently and merged back into the original *parent* model.

However, tasks have additional functionality intended to support circumscribed bits of work assigned directly other Solidatus users: you can restrict access to only parts of a model, and model *Owners* can keep track of changes throughout the lifecycle of a task.
{% endhint %}

If a task assignee needs to delegate some of the modelling effort, they can even create a task within the task, referred to as a [sub-task](#sub-tasks). When the top-level task is submitted, this also submits the changes for every sub-task.

## Who can create and perform tasks?

A task can be created by any model Owner or Author and assigned to any registered user, even if they have not been given prior access permission to a model. A task effectively gives someone temporary, sandboxed, Author access to a model.

{% hint style="success" %}
To create a task or sub-task, you must have an Author licence. To edit a model as a task assignee, you must have an Author or Practitioner license.

A user with the Practitioner licence can **only** participate in model development via tasks at the request of other users with Author licences. The Practitioner licence effectively allows organisations to extend collaborative work on models beyond the usual modeling community.
{% endhint %}

Tasks can be used to delegate the creation or validation of **all** or **only parts** of your model to others, while leaving the action of reviewing and merging changes to the task creator.

## How do tasks work?

When you create a task, Solidatus creates a new model for the task assignee(s) to work on (which is a full copy of the whole or a subset of the “master” model, depending on the options selected when the task is created).

Tasks are a type of Activity, and an Activity representing the task is created when a task is created.

The progress of a task can be monitored in the `Activities` tab in the [Model Overview](/the-user-interface/models-ui/model-overview), and via the [My Activities](/the-user-interface/models-ui/activities-interface#the-my-activities-list) page. In addition, the list of models in the [Model Browser](/the-user-interface/models-ui/model-browser) includes flag icons to show how many unresolved Activities there are for a model.

If [auto-merging](/models/share-and-collaborate/activities-and-activity-types/auto-merge) of Tasks is enabled, the changes proposed by the Task will be automatically merged into the Model, possibly following the [approvals workflow](/models/share-and-collaborate/approvals-workflow). If auto-merge is not enabled, the owners or authors of the parent model can review the proposed changes and decide which (if any) to accept and merge into the parent model, again possibly subject to the [approvals workflow](/models/share-and-collaborate/approvals-workflow).

If changes are made to the parent model during the life of the task, one or more [parent model changes](/models/share-and-collaborate/activities-and-activity-types/parent-model-changes) Activities will be raised for the task.

{% hint style="warning" %}
Be careful when merging parent model changes into a task model, as these will overwrite any changes you have already made in the task.

It is good practice to [synchronise your task model with those changes](#sync-with-parent-model) before starting a task; however, once a task has been started, it is not advised to sync with a parent model because this will overwrite changes you have already made to the task.
{% endhint %}

The Task lifecycle consists of a series of actions, some of which will change the state of the Task; the standard flow (excluding [approvals](/models/share-and-collaborate/approvals-workflow) and [closing](#closing-a-task) or reopening the Task) is depicted in the diagram below (the coloured boxes indicate the Task state when an action takes place):

{% hint style="success" %}
If the state of a Task is *Merged,* the Task model can no longer be edited. No more actions can be taken on this Task; create a new Task to continue editing using Tasks.

## Summary of actions

**In the Model Overview or Model Viewer**

* Model author or owner [creates](#create-a-task) the Task and assigns it to one or more users and/or groups
  * the scope of the Task can be restricted - see [Restricting the scope of a Task](#restricting-the-scope-of-a-task).
* The Task Model is created - this is where the work will be done
* The task state is *Open*

**The Task Assignee**

* Open the [the Activity page](#the-activity-page) for the Task

  > * in the [Activities tab](/the-user-interface/models-ui/model-overview#activities-tab) in the Model Overview
  > * from your list of [Notifications](/the-user-interface/the-navigation-bar#notification-settings)
  > * from your [My Activities page](/the-user-interface/models-ui/activities-interface#the-my-activities-list)
* Click on the `Edit Model` button
* Create and merge [Sub-Tasks](#sub-tasks) if required
* If the parent Model is saved, and the changes affect the scope of the Task, the assignee(s) can [synchronise the Task Model](#sync-with-parent-model) with the current revision of the Parent Model. However, if the Task has already been started, **do not sync with the Parent model**, as this will overwrite any changes already made.
* In the Model Viewer, save the changes - choose from two options
  * if you’re not ready to submit the Task yet, choose `Save` (the Task state remains *Open*)
  * if you **are** ready to submit the Task, choose `Save and Submit`
* When you’re ready to [submit](#submitting-a-task) your changes, either
  * choose `Save and Submit` when saving the Task Model

    or
  * click on the `Submit` button on the Model Viewer toolbar
* When the Task is **Submitted**, the task state changes to *Ready to merge* and the parent Model owner is notified; the changes for every subTask (if there are any) will also be submitted
* The Task can be reopened at any time unless the state = *Merged* (the state will change back to *Open*)

**A Model owner or author**

* If [auto-merging](/models/share-and-collaborate/activities-and-activity-types/auto-merge) has been enabled for Tasks in the parent Model, Solidatus will attempt to merge the changes into the parent model

  > * otherwise, the changes are merged into the parent Model by a Model owner or author using [Visual Merge](/models/build-and-edit-models/diff-mode#merge-differences-between-models) - open the [the Activity page](#the-activity-page) for the Task and click on the `Visual merge` button to review the differences - see [Diffing a Model](/models/build-and-edit-models/diff-mode)
  > * review the changes, deselecting any changes you do not agree with, then click on `Save` in the toolbar - this will create a new Model revision
* The state of the Task changes to *Merged*

### Notes on creating Tasks

* You **must** *assign* the Task to one or more users. You can assign the Task to any Solidatus user.

  All assignees have equal rights to edit the Task model.
* You **may** *share* the Task with one or more [Groups](/models/share-and-collaborate/groups). Group members will be able to view (not edit) the Task model.
* If the Model settings require Tasks to be approved, you **may** add one or more *Approvers* to the Task. In addition to any Approvers named in the Task, any Model Owner or Author can approve Task changes, **unless** they are listed as an Assignee.
* You **may** add one or more tags to the Task - choose from tags that have already been used for Activities in this model, or create new tags.
* `Restrict editable entities` is preselected for you if you create the Task from the Model Viewer after selecting one or more entities.

{% hint style="success" %}
The dropdown list of users to assign the Task to will be limited to those who have access to the model and may (depending on your site settings) also be limited to those users with whom you share group membership. If the name of the user is not shown, enter their email address.
{% endhint %}

{% hint style="success" %}
A user can only be nominated as an Approver if they have an [Author licence](/account-management/licences-capabilities-and-roles).
{% endhint %}

## Restrict the scope of a task

Tasks allow you to delegate the modelling effort to other users and groups of users. Much of the time, you will want to focus their attention on a subset of the model, perhaps a whole layer or a single object. You may also want to restrict the types of entity that can be edited. For example, you may want your Subject Matter Experts (SMEs) to provide the descriptions and other descriptive properties for a section of a model, without being able to create anything new. Alternatively, you may want them to add content within a selected entity.

If your working practices require you to divide responsibilities between model authors, Tasks provide an excellent way of managing change and focusing a modeller’s attention on what matters today.

If a user is a SME with a Practitioner licence, they can only participate in model development at the request of other users, via Tasks.

For example, you may ask an SME to work on the *Account* object in a business glossary, with the freedom to add, enhance, or remove anything within that context. If they have a *Practitioner* licence, you have to create a Task that is assigned to that user.

{% hint style="success" %}

* To restrict the editing scope to a specific subset of entities, select them **before** you create the task, which will automatically select the `Restrict editable entities` checkbox in the *Create task* dialogue.
* If **anything** in the Model Viewer is selected when you create a Task, the default setting is to restrict editable entities to those selected; in other words, the `Restrict editable entites` option will be pre-selected for you if anything is selected when you create the Task.
* To restrict the *types* of entity that can be edited, select `Restrict editable entities`.
* To allow the editing of entities but prevent the user from modifying transitions, select `Restrict editable entities`.
  {% endhint %}

{% hint style="warning" %}
Entities imported from another model cannot be edited via a Task.
{% endhint %}

## Sub-tasks

If the Task modeller needs to delegate some of the modelling effort, they can create a Task within the Task, referred to as a **sub-task**. The sub-task can contain further sub-tasks, which can contain sub-tasks, and so on.

The workflow for sub-tasks is the same as it is for the top-level Task - the sub-task can be submitted, may be subject to approvals, and parent changes (from the parent Task model) can be synchronised. The Task Assignee is the ‘owner’ of the Task Model, so they are able to ‘Force Merge’ changes from sub-tasks - see [Notes for Approvers](/models/share-and-collaborate/approvals-workflow#notes-for-approvers).

**When the top-level Task is submitted, this will also submit the (Approved) changes for every subTask.**

Sub-Tasks are created from the Model Viewer while working on a Task. To see a list of subTasks, open the Task from the Activities tab – they are listed in the bottom-right corner of the Task page. Click on a subTask to open it.

<figure><figcaption><p>The list of Sub-tasks</p></figcaption></figure>

## Sync with a Parent model

If the parent Model changes during the life of the Task, one or more [Parent model changes](/models/share-and-collaborate/activities-and-activity-types/parent-model-changes) Activities will be raised for the Task.

It is good practice to synchronise your Task Model with those changes **before** starting the Task; however, once the Task has been started, **we recommend not syncing with the parent Model as this will overwrite any work you’ve done on the Task**.

{% hint style="warning" %}
!Be careful synchronising a Task Model with its parent Model!

If you have already edited the Task Model, these edits be overwritten when you synchronise with the parent Model. We generally recommend not to synchronise a Task Model once it has been edited, i.e., work has begun on the Task.
{% endhint %}

## Examine task changes

There are two ways of examining the changes made during a Task, *before it is submitted*.

1. Compare the current revision of the Task Model to a previous revision of the Task Model

   The [Activity page for the Task](#the-activity-page) will list every revision for the Task, representing each occasion when the Model was saved. Click on a `new revision` link in the list to open a read-only Model Viewer window showing the state of the Task Model at that time.

   Now click on `Diff/Merge` in the toolbar - this will open the standard [Diff/Merge](/models/build-and-edit-models/diff-mode) feature, allowing you to visualise the differences between the previous revision and the current state of the model. You are also able to use the `Take New` and `Take old` buttons to see the before and after views of the model.

   If you want to undo some of the changes made recently, click on `Show n changes from the Revision` in the *Inspector* tab on the [Model Sidebar](/the-user-interface/models-ui/model-viewer/model-viewer-sidebar) - now you can select which changes to undo.
2. Compare the current revision of the Task Model with the current revision of the parent Model

   In the [Activity page for the Task](#the-activity-page), click on `View changes` to open a read-only comparison of the two models, using the standard [Diff/Merge](/models/build-and-edit-models/diff-mode) feature.

After the Task has been submitted, you can:

1. In the [Activity page for the Task](#the-activity-page), click on `View changes` to open a read-only comparison of the two models, using the standard [Diff/Merge](/models/build-and-edit-models/diff-mode) feature.
2. In the [Activity page for the Task](#the-activity-page), click on `View revision` to open a read-only view of the Task Model that was submitted.

## Submit a task

When a Task assignee decides that their changes are complete and ready to merge into the parent Model, they **Submit** the Task. This indicates to the owners and authors of the parent Model that the Task changes are complete and ready to merge into the parent Model.

When you’re ready to submit your changes, either

> * choose `Save and Submit` when saving the Task Model
>
>   or
> * click on the `Submit` button on the Model Viewer toolbar

## What happens next?

If [auto-merging](/models/share-and-collaborate/activities-and-activity-types/auto-merge) of Tasks is enabled, the changes proposed by the Task will be automatically merged into the Model, possibly following the [approvals workflow](/models/share-and-collaborate/approvals-workflow). If auto-merge is not enabled, the owners or authors of the parent model can review the proposed changes and decide which (if any) to accept and merge into the parent model, again possibly subject to the [approvals workflow](/models/share-and-collaborate/approvals-workflow).

If the Task needs to be approved, each approver will open the [Activity page for the Task](#the-activity-page). This allows each of them to:

* View the Task Model - click on `View revision`
* Approve the Task - click on `Approve`
* Reject the Task - click on `Reject`
* Revoke a previous approval - click on `Revoke Approval`
* Undo a previous rejection - click on `Undo rejection`
* A Model owner can ‘Force merge’ the changes - see [Notes for Approvers](/models/share-and-collaborate/approvals-workflow#notes-for-approvers)

Once the changes have been merged into the parent Model, the state of the Task changes to *Merged*.

## List tasks

The `Activities` tab on the [Model Overview](/the-user-interface/models-ui/model-overview) provides access to a list of Actvities for a Model, use the filter dropdown if you want to show only Tasks.

To see a list of Tasks that have been assigned to you, click on `Activities` on the [Navigation Bar](/the-user-interface/the-navigation-bar) to open your [My Activities](/the-user-interface/models-ui/activities-interface#the-my-activities-list) page. Again, use the filter dropdown if you want to show only Tasks.

## Close a task

A Task can be closed if it has not yet been merged into the model, using the [Activity page for the Task](#the-activity-page) - click on the `Close activity` button at the foot of the screen. The Task can be reopened at any time by one of the assignees or a model owner or author.

## Lifecycle with approvals

If approvals have been enabled for the Model then the [Approvals workflow](/models/share-and-collaborate/approvals-workflow) will be followed. This changes the standard lifecycle in several ways:

> * when a Task is submitted, the state changes to *Submitted* (it will not change to *Ready to merge* until it has been approved)
> * there is a review process; the changes need to be approved by one or more approvers - see the Activity page to find out who they are
>
>   > * when a sufficient number of approvers have approved the changes, the state of the Task will change to *Ready to Merge*
>   > * if **any** approver rejects the changes the state will change to *Changes requested* - the assignee is expected to make changes and then resubmit the Task
>   > * the approver who rejected the changes must approve the changes (or lose their right to approve changes) before they can be merged (unless a Model owner decides to *Force merge* the changes - see [Notes for Approvers](/models/share-and-collaborate/approvals-workflow#notes-for-approvers))

{% hint style="success" %}
Contact the model owner if you think it’s taking too long to get your Task Model approved
{% endhint %}

The approvals workflow for Tasks (apart from [closing](#closing-a-task), rejecting, or reopening the Task) is illustrated by the diagram below:

## The activity page

[The Activity page](/models/share-and-collaborate/activities-and-activity-types/activities#the-activity-page) is the ‘control panel’ for the Task, as it is for every Activity.

<figure><figcaption><p>The Activity Page for a Task</p></figcaption></figure>

The above example shows a Task, as viewed by a user assigned to the Task.

From this page the user can:

* edit the Task Model (a temporary copy of the Model created to support the Task)
* [sync the task model with the parent](#sync-with-parent-model), to ensure they have a current view of the parent Model (or at least the part of the Model they’re working on)
* view the changes to date
* [submit the Task](#submit-a-task), so the changes can be merged into the parent Model
* close or reopen the Task
* add a comment

{% hint style="success" %}
The *Contributors* section is dynamic: it starts off empty and is filled in when anyone performs an action on the task, such as saving a change, submitting the task, or merging it into the Parent model.
{% endhint %}
