# Model architecture for Data Maps

A Data Map is automatically generated when one or more Lineage models are published to a Data Domain.

As a result, the process of preparing Models for Data Maps is the same as the process of [Preparing Models for Building a Data Domain](/data-domains/understand-data-domains/prepare-models-to-publish-to-domains#why-model-preparation-matters).

The purpose of this page is to present the same information as the [Model Architecture for Domains](/data-domains/understand-data-domains/prepare-models-to-publish-to-domains) page, except from the perspective of how a Data Map works.

## Essential ingredients for a Data Map

The Data Map belonging to a domain is built from:

* **Lineage models** published to a domain
* Reference models that are published and then designated as **context models** in the domain Data Map settings.

| *Model Type*                 | *Primary Function*                                          | *What It Provides*                                                                                                                                   |
| ---------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lineage models**           | Supply data and flow information                            | <ul><li>Data entities and Data Assets</li><li>Lineage flows</li><li>Properties and Reference relationships</li></ul>                                 |
| **Context Reference models** | Enable visual grouping for business-friendly, summary views | <ul><li>Visually organise and summarise lineage</li><li>Business-friendly Data Maps</li><li>Information architecture for categorising data</li></ul> |

{% hint style="success" %}
Context models are just Reference models, and they are created and edited in the same way as other Reference models.

The key difference is that they serve a specific purpose in Data Domains.

When you designate a published Reference model as a context model in the Data Domain settings, it becomes available to apply as visual grouping mechanism in a Data Map.
{% endhint %}

To create an effective Data Map, you need:

* One or more Lineage models containing your data flows
* At least one context Reference model for business classification
* Mapped relationships between context and Lineage models

{% hint style="success" %}
Without Reference relationships between context model terms and Lineage model entities, your Data Map will show ungrouped lineage, which can be harder for non-technical and business users to understand.
{% endhint %}

See [Create and structure a context model](#create-and-structure-a-context-model) for details on how to set up Context models and map relationships correctly.

## Data Map Lineage model requirements

Lineage Models serve two key functions in Data Domains:

* **Data source**: Every entity in a published Lineage model becomes a searchable, discoverable entry in your domain
* **Lineage visualization**: Data Maps combine lineage from all published Lineage models into a single map

{% hint style="success" %}
When a Lineage Model is published to a domain, a corresponding entry in the domain is created for each Layer, Object, Group, and Attribute in the Lineage model.
{% endhint %}

Entity names in source Lineage models identify domain entries, and names can be used to find entries via

* [Searching](/data-domains/explore-data-domains/search-domain)
* [Browsing](/data-domains/explore-data-domains/browse-domain)
* [Querying](/data-domains/explore-data-domains/query-data-domains)

### Prepare Lineage models

Model preparation is an important step to ensure a domain is an optimal resource for your organisation. Before publishing Lineage models to a domain, consider the following:

#### Add essential properties

Data Domains display entity properties on the main `Overview` tab of a domain entry. It helps to include essential information that colleagues need to understand and manage your data assets:

* **Descriptions and definitions** using standard property names
* **Technical details** like data types, update frequencies, and data sources
* **Governance information** including ownership, data quality metrics, and compliance details

**Automatic property display**: Data Domains recognize specific property names and display them in dedicated areas. Any property named Description, Definition, Summary, Explanation, Notes, Details, Context, Background, Meaning, Purpose, Usage, Information, or Remarks will populate the *Description box* on the `Overview` tab of an entry. If more than one of these properties exists, the first one in the priority order listed in the previous sentence is used.

**Special governance properties**: Properties with exact names (case-sensitive) “dq pass/fail”, “dq score”, “owners”, or “pii” appear in dedicated text boxes, making critical governance information immediately visible.

#### Create meaningful relationships

Reference relationships are essential for making technical metadata accessible to business users. When you relate entities in your Lineage models to terms in Reference models published to the same domain, you enable:

* **Business-friendly filtering** of search results by Reference terms
* **Cross-model discovery** where users can find data through familiar business concepts
* **Query capabilities** using Domain Query Language to locate, count, and tag data elements

The `Related Entities` tab on each Reference term’s page displays all entities related to the term, providing a clear view of how business concepts map to technical data assets.

#### Prepare for cross-model stitching

Data Maps are designed specifically for mapping end-to-end lineage across multiple Lineage models or even across an entire enterprise-wide data landscape.

They can automatically stitch lineage together across the Lineage models published to the same Data Domain.

There are two ways to achieve this automatic stitching across Lineage models in a Data Map:

* **Data Assets**: Use FQNs to identify the same data elements in published models
* **Composite models**: Build set of composite models that altogether capture full end-to-end flow

{% hint style="success" %}
If you use Data Assets, you should not use composite models to fill in lineage between models. If you use Data Assets, publish all original atomic models to the same domain.
{% endhint %}

## Data Assets for cross-model lineage (recommended)

When the same Data Asset appears in multiple models published to the same Data Domain, the Data Map automatically consolidates all lineage the asset is involved in across these models.

For example, let’s say Model A contains a Data Asset representing a customer database, and Model B contains the same Data Asset with additional lineage to downstream systems. If Model A and Model B are published to the same domain, the Data Map will show a blue Transition between the asset in Model A and the same asset in Model B, thus completing the full lineage path from source to target.

{% hint style="success" %}
Assets are considered the same when their FQNs are identical (case-sensitive), whether they are in the same model or different models.
{% endhint %}

To ensure that the Data Map stitches together lineage across models, you need to ensure that the FQNs of the same Data Asset are identical in all models.

Since Data Maps are designed to exceed the performance limitations of the Model Viewer, using Data Assets to build an end-to-end Data Map is more efficient than using composite models. It also requires less manual effort to set up.

Data Maps automatically create a **blue, two-way Transition** to represent that entities in the Data Map are the same Data Asset.

<figure>Blue transitions show that two items are the same Data Asset<figcaption><p>Blue transitions show that two items are the same Data Asset</p></figcaption></figure>

{% hint style="success" %}
If you use Data Assets to build a Data Map, you do not need to create composite models to fill in lineage between models. Publish the original atomic models to the same Data Domain, and the Data Map will automatically stitch together lineage across models that contain the same Data Asset.
{% endhint %}

### Implementation workflow

1. **Select your models**: Identify models that you want to link together in a Data Map
2. **Configure Data Assets**: Ensure FQNs of the same Data Assets are identical across models
3. **Add business context**: Create reference relationships to context model terms
4. **Test integration**: Publish to a domain and open the Data Map to verify the stitching
5. **Iterate and improve**: Refine Data Assets and relationships as needed

## Composite models for cross-model lineage

Data Maps automatically consolidate lineage for entities that have been imported into more than one published model. This enables you to use a set of composite models to stitch together lineage across models that contain the same entities.

The cross-model stitching process can be illustrated with an example:

Let’s say we have two atomic Lineage Models, `A` and `B`. A Data Map cannot represent the lineage between entities in `A` and entities in `B` unless this lineage has been worked out through Transitions between entities in `A` and `B` in a composite Model that is made up of both: `A-B`.

Let’s add two further atomic Models, `C` and `D`. For Data Maps to show lineage across entities in `A`, `B`, `C`, and `D`, the uninterrupted flow of this lineage has to be captured across these Models.

One way this could be achieved is to build a very large composite Lineage Model into which all entities in all models have been imported and to fill in the lineage between them: `A-B-C-D`. However, this is not a practical solution as models containing more than 1 million entities can cause performance issues in the Model Viewer.

Data Maps offer a better way to do this. You can build smaller composite Lineage Models that together capture all lineage when stitched together: `A-B`, `B-C`, `C-D`. A Data Domain can then be built from these three smaller composites, and the Data Map for that Domain would show all lineage from `A` to `D` and in between.

<figure>Stitch entity lineage in composite models in preparation for Data Maps<figcaption><p>Stitch entity lineage in composite models in preparation for Data Maps</p></figcaption></figure>

No individual composite model in this example contains the full lineage from Objects A to D, but altogether they do. The Data Map for a Data Domain to which these composite models are published would automatically stitch the composites together.

<figure>Data Maps stitch lineage together across composite models that contain the same entities<figcaption><p>Data Maps stitch lineage together across composite models that contain the same entities</p></figcaption></figure>

{% hint style="success" %}
Once you’ve created a set of composite Lineage models that altogether capture end-to-end lineage, only these composite models should be published to a single Data Domain.
{% endhint %}

In other words, to avoid duplication, do not publish both the original atomic models and the composite models into which the original atomics have been imported.

Here is the same Data Map fully expanded to show end-to-end lineage at the Object level.

## Data Map context model requirements

### What is a c*ontext* Reference model?

A c*ontext* Reference model is simply an ordinary Reference Model, but one built for the purpose of visually organising and summarising lineage in a Data Map.

<figure>Context models embed lineage in grouping boxes to provide meaningful business context<figcaption><p>Context models embed lineage in grouping boxes to provide meaningful business context</p></figcaption></figure>

{% hint style="success" %}
When you apply context to a Data Map, entities are embedded in expandable grouping boxes according to terms they are related to in a *context* model.
{% endhint %}

You can publish as many *context* Reference models to a Data Domain as you like (see [Add multiple context models to a domain](#add-multiple-context-models-to-a-domain)), and you can alternate between layouts provided by distinct *Context* models when viewing a Data Map.

Here are examples of *context* model classification categories (and sub-categories) for information architecture and for grouping lineage in a Data Map:

* Systems -> Oracle Mortgage DB
* Regions -> EMEA -> Singapore
* Data Owners -> North America -> Joe Bloggs
* Products -> Lending -> Credit Cards

### How do context models work?

When you designate a Reference model published to a Data Domain as a context model, the Lineage Models published to the Data Domain are scanned for Reference Relationships to terms in the Context model.

{% hint style="success" %}
For instructions on how to designate a Reference model that has been published to a domain as a *Context* model, see create-data-domains.
{% endhint %}

When a *Context* is applied to a Data Map, Lineage model entities are grouped within expandable boxes that represent the terms from the context model to which they are related.

Let’s look at an example that illustrates how applying a context affects a Data Map visualisation.

<figure>This is a Data Map with no Context applied<figcaption><p>This is a Data Map with no context applied</p></figcaption></figure>

This Data Map has no context groupings applied. Initially, it displays only the Layers in all Lineage models published to the domain.

Top-level entities in the Data Map are Layers, and these can be expanded to view Objects, Groups, and Attributes.

Other than aesthetic and navigational differences, the only difference between a Data Map and the Model Viewer is that the Data Map displays entities and lineage captured in **all Lineage models** models published to a domain.

When a context is applied, the Lineage model Layers are replaced by clickable, expandable boxes representing terms in the context model to which Lineage entities are related.

<figure>This is a Data Map with Context applied<figcaption><p>This is a Data Map with context applied</p></figcaption></figure>

As you can see, the lineage entities in a Data Map with no context have been replaced by high-level grouping boxes that still display Transition arrows representing the lineage that exists between the entities embedded in them.

### Create and structure a context model

Recall that a context model is a Reference model, but one built to provide both a classification structure for a Data Domain and visual organisation for a Data Map.

As a result, creating a context model is no different from creating any other Reference model: click **Create** in the top-right of the Model Browser and select **Reference Model**.

Before building a context model, it will be helpful to think about the terms, categories, and processes that best capture how data is organised and used in your company, and how you want to organise metadata in your domain.

When you’ve decided on the appropriate context to apply to the Lineage entities in a Data Domain, simply create a new Reference model, add entities to the Model that match the terms and structure you wish to capture, and save the model.

Then create Reference relationships between the terms in your context model and entities in the Lineage models published to the same Data Domain.

There are a few key points to keep in mind when structuring a context model:

* The simplest context model structure, which is the easiest to configure for a Data Map, is one in which all context terms are entered as **Layers** in the model.

This generates single-level context grouping boxes in which related lineage entities are embedded and appear when you expand the grouping box.

<figure>../../_images/expand-context-box.png<figcaption></figcaption></figure>

* If context terms are Objects, Groups, or Attributes in the context model, the Data Map generates *nested* context grouping boxes in which related lineage entities will be embedded.

<figure>../../_images/expand-nested-context-box.png<figcaption></figcaption></figure>

{% hint style="success" %}
Visual grouping categories can be entered as Layers, Objects, Groups, or Attributes in the *Context* Reference Model.
{% endhint %}

Note that the hierarchical structure of model entity types will generate hierarchically embedded visual grouping boxes in a Data Map, and this hierarchical structure should of course match accurately the relevant structure of the context that is provided.

### Map relationships to a context model

Relationships that you create between entities in published Lineage models and terms in published context models determine how a Data Map will appear when a context model is applied.

**Relationships** *do not* **have to be created between every entity in published Lineage models and terms in a** **context model**.

The context grouping that an entity appears in is determined by the term that the entity’s highest-level ancestor is related to in the applied context model. For example, if a Layer is related to a context model term, all descendants of the Layer will be embedded in the same context box automatically.

This principle results in a few rules for mapping context terms to Lineage models.

{% hint style="success" %}
To ensure a Data Map can apply visual context from a context model, the key rules to keep in mind are:

1. An entity cannot be related to more than one term in a context model.
2. If an entity is related to a term in a context model, none of its descendants or ancestors can be related to a different term in the same context model.
   {% endhint %}

The reason for the second rule is that entities inherit their context grouping from the highest-level ancestor that has a Relationship to a term in a given context model. As a result, a Data Map cannot render a context visualisation if an entity is related to a different context model term from a descendant or ancestor entity.

**Relationships to context model terms can be created at any level, but keep in mind the second rule**

You can create relationships between context model terms and Layers, Objects, Groups, or Attributes in a Lineage model, but be careful not to mix the level at which relationships are created within the same hierarchy.

{% hint style="success" %}
It is generally simplest to select an entity type – Layer, Object, Group, or Attribute – and only add *Context* relationships to entities of that type in the set of Lineage models published to a single domain.
{% endhint %}

This is only a general principle to ensure there are no errors and the Data Map renders applied context groupings clearly and simply.

For more complex cases in which different entity types are to be embedded in different context model categories, alternatives can be attempted. For example, you can create a context relationship to a Layer and then to only Objects in another Layer, and at the Attribute level for another Layer.

The important rule is to avoid relating an entity to a context model term that is different from the term a descendant or ancestor is related to.

{% hint style="success" %}
If you create relationships to context model terms at the Object level, Objects in the same Layer can be grouped into different context model categories.
{% endhint %}

Recall that all descendants of an Object will be embedded in the same context grouping as the Object.

For general instructions on how to create reference relationships between a Lineage model entity and a Reference model term, see [Add and edit reference relationships](/models/build-and-edit-models/add-and-edit-reference-relationships).

### Map relationships to nested context terms

If reference terms are Objects, Groups, or Attributes in a context model, a Data Map embeds related lineage entities inside nested context grouping boxes.

Let’s illustrate this with another example:

An organisation has a products division that manages a set of lending products, one of which is mortgages. In this scenario, mortgages are located within a hierarchical structure of product domains (Products > Lending > Mortgages).

The *Context* Model should represent this using the hierarchical structure of entity types in a model:

* **Products** is a Layer
* **Lending** is an Object in the **Products** Layer
* **Mortgages** is an Attribute within **Lending**

<figure>Create Relationship to Hierarchical Grouping<figcaption><p>Create Relationship to Hierarchical Grouping</p></figcaption></figure>

When reference relationships are created between entities in Lineage models and the Attribute **Mortgages** in the context model (and these models are published to a Data Domain), the lineage entities will be embedded in *nested* context grouping boxes.

Hierarchical context groupings enable you to embed technical lineage in organisational structures that consist of tree-like domains and sub-domains.

{% hint style="success" %}
You can use nested grouping categories to integrate what are usually separate business, conceptual, logical, and physical models into one interactive Data Map visualisation that contains all model types and shows their relationships.
{% endhint %}

### Unmapped entities

It may be the case that some entities in Lineage Models published to a Data Domain have not been mapped to any terms from a *Context* Model that has been applied to the Data Map. When you apply the *Context* model to organise the Data Map layout, what will happen?

Data Maps will group all unmapped entities into a grouping box with the name **Untagged**.

{% hint style="success" %}
Since entities inherit the *Context* grouping category of their ancestors, “untagged” entities are entities whose ancestors are also unrelated to any *Context* term.
{% endhint %}

### Add Context models to a domain

Recall that a context model is just an ordinary Reference model, but one that you set up to function as a context model in a Data Domain.

Once you’ve built your context model and mapped relationships to the Lineage models in a domain, you then need to add it to the domain.

{% hint style="success" %}
You can add a context model when you create a domain, or you can add it later through the domain `Settings`.
{% endhint %}

To add a context model to a domain:

1. Navigate to the `Settings` of the Data Domain (see [Edit a Data Domain](/data-domains/build-data-domains/edit-data-domains)) or create a new domain.
2. Publish the Reference model you designed to be a *Context* model in the `Models` tab.
3. Once you’ve published it, it will appear in the `Data Map` tab.
4. Select the checkbox next to the model in the `Data Map` tab.

The `Data Map` tab of the domain settings contains **all and only** Reference models that you published in the `Models` tab.

In the `Data Map` tab, you can designate Reference models to function as context models, i.e., to use for visual business context in the Data Map.

<figure>Select *Context* models for use with the Data Map<figcaption><p>Select <em>Context</em> models for use with the Data Map</p></figcaption></figure>

Designating a model as a context model makes it available in the list that appears when you open a Data Map.

Note that this list is the same as the list in the dropdown menu at the top-left of a Data Map. You can also apply visual context, or switch the applied context, using the dropdown.

<figure>Select Context to apply to a Data Map<figcaption><p>Select Context to apply to a Data Map</p></figcaption></figure>

### Add multiple context models to a domain

By publishing multiple context models to a Data Domain, you can easily visualise the same set of Lineage models grouped in different ways to match unique classification contexts.

{% hint style="success" %}
Multiple context Reference Models provide different high-level perspectives from which to understand the same data entities and lineage.
{% endhint %}

To add multiple context models to a domain:

1. Create multiple Reference models to use as context models.
2. Create reference relationships from the same set of Lineage models to relevant terms in these Reference models.
3. Publish all Reference models and Lineage models to the same Data Domain.
4. Designate the Reference models to function as context models in the `Data map` tab of the domain settings.

{% hint style="success" %}
If you want to include multiple higher-level classification vocabularies (i.e. Systems, Regions, Products) in your Data Domain, it is best to use a distinct context model for each vocabulary, rather than add all to one single Reference Model.

When terms representing different contexts are in separate context models, you are able to switch between visual groupings of the same lineage by selecting a different context model to apply to the same Data Map.
{% endhint %}
