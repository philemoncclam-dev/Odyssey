# Reference models 101

Reference models enable you to document data and lineage flows in relation to broader semantic frameworks, such as regulatory principles or business terms, that give meaning to technical systems and data structures represented in lineage models. Developing and applying consistent reference terms and concepts allows you to create a unified view of diverse technical data landscapes within a business.

At a basic functional level, reference models allow you to relate data entities in multiple lineage models to the same set of reference terms, whether they are business glossaries, regulatory frameworks, governance structures, or any other semantic classification.

While lineage model entities can only be connected to other lineage entities in the same model, via the visible directional arrows we call **Transitions**, entities in reference models can be connected to unlimited entities (or terms) in other models via **reference relationships**.

Lineage and reference models look the same and function the same in all other respects, but **reference relationships** provide unique possibilities for managing and governing the physical data lineage landscapes represented in Lineage models.

## Reference relationships: Key elements

Each **Reference relationship** consists of three things:

1. An **entity** (or it can also be another term) in model
2. A **term** in a separate reference model (for clarity, we refer to entities in reference models as terms)
3. A **label** that describes the meaning of the relationship between the entity and term.

The following phrases help capture the semantics of Reference relationships:

* “An entity is related to a Reference term under a label”
* “A Reference relationship *has* a label”
* “There is a relationship *from* an entity *to* a Reference term *with* a label”

{% hint style="success" %}
The semantic distinction between **term** and **entity** makes life easier when we’re discussing different ways to connect ‘things’ in Solidatus.

When we mention ‘related terms’, for example, we know we’re talking about linking things that are defined in different models, not about linking things *within* a model using Transitions.
{% endhint %}

Thanks to Reference relationships, you can store reference content in a Reference model and use the same content to document and describe the physical data and lineage contained in an unlimited number of Lineage models.

## Reference model example: Documenting business concepts and GDPR classifications

To help understand how and why to use reference models, let’s start with examples of two models containing:

> 1. Enterprise-agreed Concept definitions
> 2. GDPR and other Data Privacy and Protection considerations.

These models do not contain entities representing **physical** data elements like databases, tables, columns, or files. Instead, they contain **reference** metadata that puts physical data and physical data lineage into a meaningful business or regulatory context.

We often refer to reference content as the “semantic world” of an organisation. For example, reference metadata can include business semantics, governance or ownership roles, functions, policies, or regulations. Reference relationships help link the “semantic world” to the “physical world” of data storage, transformation, flow, analytics, and reporting.

By defining business *Concepts* and *GDPR definitions and classifications* in **Reference models** and using **Reference relationships** to link them to physical data entities, we are able to:

> **Apply Governance**
>
> * Provide a consistent and uniform classification architecture that can be applied to multiple Lineage models
> * Recognise that organisational responsibilities for Concepts and GDPR definitions and classifications are different from organisational responsibilities for physical data and data lineage
> * Ensure classifications are only defined by the right people and functions
> * Add further metadata (in the form of Properties of Reference terms) to Concepts and GDPR classifications
> * Allow any user with *Viewer* access to the Reference models to use them to classify entities in their own models
> * Provide common analysis methods by sharing Filters and Display Rules involving Reference content, knowing they will always work
> * See how and where Concepts and GDPR classifications are being used across the data landscape of an enterprise
>
> **Conduct analysis within a Lineage model**
>
> * Use the [Model Viewer](/the-user-interface/models-ui/model-viewer) to see where each Concept and GDPR classification has been referenced in a Lineage model - the Labels of a Reference relationship can tell us *why* the relationship exists
> * In the [Model Viewer](/the-user-interface/models-ui/model-viewer), we can use use [Aggregate by Reference Label](/additional-resources/advanced-topics/aggregate-attributes-by-property-or-reference-label) to group entities according to their Reference relationships to terms in a chosen model
> * Use the [Lineage Explorer](/models/explore-and-analyse-models/lineage-explorer) to create a view of a subset of a Model based on Relationships to Reference Models

## Scenarios for using Reference models

Here are a few examples of modelling scenarios where a Reference model would be appropriate:

> * Anything metadata classification has its own metadata, and/or traceability across models is required
> * CDE Taxonomies (dictionaries)
> * Authoritative Data sources
> * Processes
> * Business structure
> * general Metadata Governance models
> * Business Rules
> * Business ‘objects’ or Concepts, perhaps in a taxonomy
> * Data Protection / Privacy classifications (e.g. GDPR Principles and personal data classifications)
> * Enterprise Architecture artefacts (likely to be a complex Model with multiple layers)
> * Data Quality Dimensions
> * Data Quality Control Databases
> * Employee Names, Roles and Responsibilities
> * Regulations & Legislation
> * Business Definitions eg Business Products

## Reference model types

Solidatus allows you to indicate the purpose of a Reference Model by selecting from a list of types:

> * Asset Inventory
> * Business Glossary
> * Data Dictionary

However, choosing a type **makes no difference** to how the Reference Model will work; it’s just a label, and all Reference model types function in the same way.

Choosing a type makes it easy to identify the purpose and content of a Reference Model, as the type is displayed in the list of models in the [Model Browser](/the-user-interface/models-ui/model-browser), and also when creating or viewing Reference Relationships.

A Reference Model’s type can be changed at any time by editing model information in the Settings tab in the [Model Overview of a Reference model](/the-user-interface/models-ui/build-reference-models).

### Avoid model reconfiguration

The longer you wait before using Reference Models, the more problems you’re likely to face in your day-to-day modelling, and the trickier it will be to introduce Reference models later.

For example, assume you’re modelling your database structures and other data architecture artefacts, and cross-referencing them to *Critical Data Elements* (CDEs) using properties. You’re almost certain to have multiple versions of at least one CDE due to:

> * Spelling mistakes
> * Punctuation – different use of word case and spacing and commas or speech marks
> * Variations of wording but essentially meaning the same thing
> * Incorrect entries – where values which are clearly not CDEs have been entered in the wrong property
> * When a CDE is renamed, we can’t update all affected Lineage Models, without running queries to search the Models
> * Different Models use different Property Names \* CDE \* Cde \* CRITICAL DATA ELEMENT \* Critical Data Element

The common feature here is the lack of control over what individuals are typing into their models. Using Reference models will help you avoid having to reconfigure properties for multiple models when something changes.
